# WebFinChat

React-клиент, Vite для разработки и сборки, `server.mjs` для production.
Исходный код для DEV, TEST и PROD: https://github.com/zpvision/webfinchat, ветка `main`.
Различия окружений задаются переменными окружения, без правок исходников на серверах.

## Установка из чистого клона

Требуется Node.js 22.12+ ветки 22 или Node.js 24+ и npm. Проверено на Node.js 24.13.0 / npm 11.6.2.

```sh
git clone https://github.com/zpvision/webfinchat.git
cd webfinchat
npm ci
npm test
npm run build
npm start
```

Перед запуском задайте параметры своего окружения через менеджер процессов/служб
или создайте локальный `.env` по `.env.example`. Не используйте демонстрационный API-ключ
из примера. Для локальной разработки: `npm run dev`.
В PowerShell при блокировке `npm.ps1` используйте `npm.cmd`.

`npm start` обслуживает `dist` и необходимые HTTP/WebSocket-прокси.
`npm run preview` предназначен для просмотра сборки и не заменяет этот сервер.
Публичный сайт должен работать через HTTPS; существующий reverse proxy должен
передавать `/finchat-channels` с WebSocket Upgrade и остальные запросы в Node.js.

## Конфигурация окружений

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `FINCHAT_HOST` | Хост backend без схемы и пути; серверные file/WebSocket-прокси | `api.dev.finchat.club` |
| `FINCHAT_API_KEY` | Ключ приложения FinChat для HTTP/WebSocket-прокси и браузерной сборки, если нет `VITE_FINCHAT_API_KEY` | пусто |
| `PORT` | Порт `npm start` | `4173` |
| `LIVEKIT_URL` | Разрешённый адрес LiveKit для CSP production-сервера; только `wss://` | `wss://call.finchat.club` |
| `MAX_FILE_BYTES` | Максимальный размер загружаемого файла в байтах | `52428800` |
| `MAX_DOWNLOAD_BYTES` | Максимальный размер скачиваемого тела, включая распакованное | значение `MAX_FILE_BYTES` |
| `ALLOWED_ORIGINS` | Дополнительные разрешённые Origin WebSocket, через запятую; свой origin разрешён | пусто |
| `VITE_FINCHAT_HOST` | Переопределение адреса прямого подключения браузера, параметр сборки | `FINCHAT_HOST`, затем `api.dev.finchat.club` |
| `VITE_FINCHAT_API_KEY` | Переопределение **публичного** ключа браузера, параметр сборки | `FINCHAT_API_KEY`, затем пусто |

Восстановлена схема, работавшая до изменения конфигурации: браузер напрямую
подключается к backend с адресом и ключом, заданными при сборке. HTTP file-прокси
по-прежнему читают `FINCHAT_HOST` и `FINCHAT_API_KEY` при запуске сервера.
Для DEV/TEST/PROD собирайте `dist` с параметрами соответствующего окружения.
После изменения адреса или ключа выполните `npm run build` и перезапустите сервер.
Адрес комнаты и временный LiveKit JWT по-прежнему приходят из backend звонков.
Секреты LiveKit этому репозиторию не нужны.

Vite читает `.env`, `.env.local`, `.env.[mode]`, `.env.[mode].local` при сборке/разработке.
`server.mjs` читает только `.env` в рабочем каталоге при запуске.
Непустые переменные процесса имеют приоритет. В `server.mjs` пустое значение,
как и раньше, заполняется из `.env`; у Vite сохраняются стандартные правила `loadEnv`.
Для production используйте рабочий каталог репозитория, содержащий `dist`.

Ключ приложения, выбранный для браузера (`VITE_FINCHAT_API_KEY` либо `FINCHAT_API_KEY`),
встраивается в JS и доступен посетителям, как в прежней реализации. Для этих параметров
используйте только предназначенный для клиентов ключ FinChat, а не приватные ключи
LiveKit или другие серверные секреты. Совместимость CSP и Origin с backend обязательна.

## Обновление и откат

1. На DEV/TEST получите нужный commit из `main`; проверьте `git status --short`.
   Не переносите серверные исправления вручную и не выполняйте `git reset --hard`
   поверх неизвестных локальных изменений. Сначала сохраните и разберите их.
2. Выполните `npm ci`, `npm test`, `npm run build`. Сохраните SHA проверенного commit.
3. На TEST проверьте вход, сообщения, скачивание вложения/PDF и звонок двумя аккаунтами.
4. На PROD используйте тот же проверенный commit или артефакт сборки, задайте production
   environment и перезапустите существующую службу. Локальную правку `Content-Length`
   больше применять не требуется.
5. Для отката используйте прежний проверенный commit/артефакт с его конфигурацией.

Не коммитьте `.env*` (кроме `.env.example`), ключи, `node_modules`, `dist`, логи,
`test-results` и временные файлы. `.gitignore` не защищает уже отслеживаемые файлы:
перед публикацией проверяйте `git diff --cached` и `git ls-files --cached --ignored --exclude-standard`.

## Уведомления о сообщениях

Новое сообщение из другого чата или при неактивной вкладке показывает карточку
с названием чата и коротким текстом, сопровождается коротким звуком и, при наличии
разрешения, системным уведомлением. Нажатие открывает нужный чат, даже если ранее
список был отфильтрован поиском. В открытом активном чате уведомления не дублируются.
История, собственные сообщения, редактирование, записи звонков и повторные пакеты
после переподключения не вызывают сигналов. Серии сообщений ограничены по частоте звука.

Доступ к системным уведомлениям включается кнопкой колокольчика в списке чатов;
при запрете разрешите уведомления в настройках сайта браузера.
Звук разблокируется при взаимодействии со страницей; если он заблокирован,
доступна кнопка «Включить звук сообщений».
Это уведомления открытого веб-клиента, без фонового push после закрытия вкладки.
Используются [Notifications API](https://notifications.spec.whatwg.org/) и
существующий Web Audio механизм с учётом [autoplay policy](https://developer.chrome.com/blog/autoplay/).

## Проверки

HTML (включая SPA-маршруты) отдаётся с `Cache-Control: no-store`, файлы Vite
с хэшем в `/assets/` — с длительным `immutable`, остальные статические файлы — `no-cache`.
Адрес `/service-worker.js` зарезервирован для удаления прежнего Tinode worker:
он возвращает JavaScript с `no-store`, а не HTML оболочки приложения.
FinChat не регистрирует новый worker; при старте снимает только старую регистрацию
`/service-worker.js` со scope `/` на своём origin. Сессии, черновики, cookies,
кэши и регистрации других приложений не очищаются, открытые чаты не перезагружаются.

При ошибке отправки файла HTTP-прокси возвращает `X-Finchat-Upload-Stage`
(`request`, `presign`, `storage`, `multipart`, `complete`) и `X-Finchat-Upload-Request-Id`.
Ошибка в интерфейсе содержит понятное название этапа и код диагностики.
В логах Node.js/Vite строка `[finchat-upload]` связывает код с HTTP-статусом,
хостом backend и наличием API-ключа, без ключей, токенов, подписанных URL и тела ответа.
Порядок разбора: [docs/upload-troubleshooting.md](docs/upload-troubleshooting.md).

Если подготовка direct upload возвращает HTTP 400 с `ctrl.code=400` и
`ctrl.text=malformed`, прокси один раз пробует стандартный Tinode multipart upload
в тот же backend. При этом ответ содержит `X-Finchat-Upload-Mode: multipart`.
Работающий direct upload, API-ключ и представление пользовательского токена сохранены.
На отказ авторизации, лимит размера, другой ответ 400 или ошибку storage эта попытка
не выполняется. Multipart-ошибка также не запускает повторов.

- `npm test`: существующие тесты сообщений/очереди и звонков, а также HTTP-интеграция
  реальных production/DEV file-прокси с локальным backend: gzip/Brotli/deflate,
  пустое тело, chunked, PDF, ошибки, ограничения размера и upload; WebSocket forwarding;
  приоритеты исходной конфигурации браузерного ключа и `.env`.
- `npm run test:browser`: Chrome, сценарии прокрутки и переподключения с локальным
  транспортом; нужен установленный Chrome или `FINCHAT_TEST_BROWSER`.
  Используется commit `27cc83d` для сравнения, поэтому требуется история Git.
  Также проверяются карточка сообщения, Web Audio, переход в чат и отсутствие дублей;
  системный Notification API подменяется, интерфейс ОС нужно проверить вручную.
  `FINCHAT_REVIEW_SKIP_BENCHMARK=1` пропускает замеры производительности, сохраняя проверки поведения.
- `npm run build`: production-сборка. Отдельный lint не настроен.
- `npm run test:browser:cache`: Chrome/Chromium, воспроизведение страницы старого
  worker при уже обновлённом сервере, проверка снятия регистрации через frontend
  и обновление старого script URL, сохранения сессии и черновиков.

После `fetch()` тело может быть распаковано, а upstream `Content-Length` остаться
размером сжатого ответа. Поэтому download-прокси отправляет длину полученного Buffer;
`Content-Encoding` upstream не переносится. PDF и upload уже используют фактическую длину.
Описание поведения: https://github.com/nodejs/undici/issues/2514.
