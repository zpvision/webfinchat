# HTTP 400 malformed при загрузке файла

Проверка 22.10.2026 выполнена без действующего пользовательского токена.
Использованы искусственные токены с заведомо неверной подписью; файлы не загружались,
конфигурация и процессы DEV/PROD не изменялись.

Результаты запросов к DEV:

| Сценарий | HTTP | Ответ |
| --- | --- | --- |
| Backend без API-ключа | 403 | valid API key required |
| `/file-upload-proxy` без пользовательского токена | 401 | Missing FinChat token |
| `/file-upload-proxy`, стандартный Base64, неверная подпись | 401 | authentication failed |
| `/file-upload-proxy`, base64url без padding, неверная подпись | 400 | malformed |
| Те же байты последнего токена, преобразованные в стандартный Base64 | 401 | authentication failed |

Эти ответы показывают, что в проверенном пути DEV серверный API-ключ принимается,
а HTTP auth не принимает все представления Base64. Они **не доказывают**, что
именно такой формат был у токена пользователя, сообщившего об ошибке.
Без действующей пользовательской сессии нельзя подтвердить реальную отправку вложения.

Добавлена общая функция `server/finchatHttpAuth.mjs`, применяемая в `server.mjs`
и DEV-прокси `vite.config.js` для upload, download и PDF preview:

- `-` / `_` преобразуются в `+` / `/`, восстанавливается padding `=`;
- стандартный Base64 остаётся прежним, байты секрета не меняются;
- неприменимый формат остаётся для существующей обработки ошибки backend;
- браузерное хранилище, WebSocket авторизация и API-ключ не изменяются;
- ключ и токен не передаются в Object Storage.

В локальных HTTP-тестах backend теперь отвергает неподходящий формат токена.
Добавлены проверки URL-safe и непаддированных токенов для upload/download/PDF
в production- и DEV-прокси, передачи API-ключа и отсутствия credentials в storage.
`npm test`: 120/120; `npm run build`: успешно.

После обновления кода требуется перезапуск Node.js/Vite, поскольку исправление
находится в HTTP-прокси. Проверить отправку файла с реальной сессией на DEV.
Если HTTP 400 сохраняется, нужна запись backend для соответствующего времени,
например причина отказа `media upload`; убрать из неё секреты и query string.
Не считать проблему конкретного аккаунта подтверждённо устранённой до этой проверки.

Для справки: [публичный контракт file upload](https://github.com/sotarev/chat/blob/master/swagger.yaml),
[декодирование HTTP auth в исходном Tinode](https://github.com/tinode/chat/blob/master/server/hdl_files.go).
Поведение используемого FinChat проверено отдельными запросами выше; исходный Tinode
не рассматривается как точная копия развёрнутого backend.
