# Ошибка отправки файла HTTP 400 malformed

Причина пользовательской ошибки пока не установлена. Возврат прежней схемы
API-ключа и откат преобразования токена, по сообщению пользователя, не помогли.
Они не рассматриваются как исправления этой ошибки.

Текущий путь загрузки:

1. Браузер отправляет бинарный файл в `/file-upload-proxy`, передаёт MIME,
   расширение и пользовательский токен в прежних заголовках.
2. Node.js запрашивает `POST /v0/file/u?direct=true&ext=...` либо `mime=...`
   с серверным `X-Finchat-APIKey` и `X-Finchat-Auth`.
3. После получения ссылки сервер делает PUT файла в Object Storage с выданными
   Content-Type/Cache-Control. Ключ и токен FinChat туда не передаются.
4. Только после успешной загрузки клиент публикует сообщение с URL вложения.

В публичной [спецификации FinChat](https://github.com/sotarev/chat/blob/master/swagger.yaml)
для шага 2 указаны media handler `s3_multibucket` и `direct_upload: true`.
В исходном [Tinode multipart-обработчике](https://github.com/tinode/chat/blob/master/server/hdl_files.go)
`400 malformed` также возвращается при отсутствии multipart-файла. Это возможная
ветка отказа, а не доказательство причины на развёрнутом FinChat.

## Как получить точную причину

После получения кода из Git пересоберите frontend и перезапустите Node.js
(при разработке — Vite). Изменение только `dist` не обновляет HTTP-прокси.

Повторите отправку одного файла и сохраните:

- новый текст ошибки из интерфейса;
- `X-Finchat-Upload-Stage` и `X-Finchat-Upload-Request-Id` из ответа в Network;
- соответствующую строку `[finchat-upload]` в логе веб-сервера;
- строку backend FinChat `media upload` / `malformed` за то же время, если доступна.

Не присылайте Request Headers целиком, ключ, токен или URL авторизации/storage.

Если этап `presign`, файл в storage ещё не отправлялся. Нужно выяснить причину
отказа backend: авторизация, поддержка direct upload, параметры запроса, маршрут
и фактически работающая версия backend. Уточнить, работает ли скачивание старого
вложения: это помогает отделить общую HTTP-авторизацию от подготовки загрузки.

Если этап `storage`, presign уже прошёл; проверяются выданный метод, подписанные
Content-Type/Cache-Control и ответ storage. Повторять выдачу presign или менять
API-ключ наугад не нужно.

Если новых заголовков нет, сначала проверьте обновление и перезапуск именно того
процесса Node.js, который обслуживает `/file-upload-proxy`, и передачу заголовков
reverse proxy.

В этом изменении параметры загрузки, API-ключ, токен и схема HTTP-запросов не менялись.
Добавлены диагностика и тесты отказов на двух разных этапах. Локальные тесты используют
имитацию backend/storage и не подтверждают отправку с реальной пользовательской сессией.
